# Validation Report Contract

## Purpose

This document defines the expected structure of a validation report generated by OpsPilot Core for local UI display and SQLite persistence.

## Report schema

```json
{
  "report_id": "string",
  "created_at": "ISO-8601 timestamp",
  "source_file_name": "string",
  "source_type": "ci_log | dockerfile | kubernetes_yaml | security_input",
  "summary_status": "PASS | FAIL | WARNING",
  "findings": [
    {
      "rule_id": "string",
      "severity": "INFO | WARNING | FAIL",
      "status": "PASS | FAIL | WARNING",
      "description": "string",
      "evidence": "string",
      "location": "string or null"
    }
  ],
  "metadata": {
    "input_size_bytes": 0,
    "rule_set_version": "string",
    "analysis_mode": "local"
  }
}
```

## Contract rules

- `report_id` must be unique per validation run.
- `summary_status` must reflect the aggregate outcome of all findings.
- Each finding must include a unique `rule_id`, severity, description, and evidence.
- `evidence` must be derived from the original input content or a relevant excerpt.
- `source_type` must map to a supported local validation domain.
- The schema must be preserved in SQLite history records so the same report can be displayed later without reprocessing the original file.

## Security rule ownership and deduplication

- Security findings MUST be owned by the approved `security` rule family and MUST use a canonical `rule_id` that is unique to that family.
- Docker and Kubernetes validators MAY reuse shared security-check logic or call common security helpers, but the final report MUST emit only one canonical security finding per issue.
- Duplicate security findings are determined by the final canonical security `rule_id`, matched resource or location, and supporting evidence; duplicate results must be collapsed before persistence or UI display.
- Security findings MUST continue to include the required `rule_id`, severity, description, and evidence values in the final report contract.

## User interface contract

The Streamlit interface should present the same information as the JSON contract, aligning the dashboard view with the stored report.

- Summary card: status, timestamp, and file metadata
- Findings list: each item with rule ID, severity, description, evidence, and location
- History panel: list of recent stored reports from SQLite
- Error panel: user-facing validation errors for unsupported inputs and invalid file content

## Safety constraints

- No uploaded content may be executed.
- No automatic infrastructure changes may be triggered by the report.
- The report schema is for inspection only and is never used as an execution contract.
